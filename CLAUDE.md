# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A local single-user Flask web app that automates reward-farming market making on Polymarket. The end user is non-technical: they double-click an executable, a browser opens, they enter wallet private keys, and the app places/monitors orders to earn liquidity rewards. UI strings and user-facing messages are in 简体中文 — keep them that way. Intended to be packaged as a single exe via PyInstaller.

## Commands

```powershell
pip install -r requirements.txt   # also need pytest for the test suite
python app.py                     # run app; opens browser at http://127.0.0.1:5000 (/setup on first run)
pytest                            # run unit tests
pytest tests/test_strategy.py     # single file
pytest tests/test_strategy.py::TestMaxSpread2_TickSize1Cent::test_bid1_gt_2000_place_at_bid2  # single test
```

`tests/` holds pytest unit tests (pure logic, no network). The top-level `test_live.py`, `test_simulate.py`, `test_real_order.py` are **not** pytest tests — they are manual scripts that hit the real Polymarket API and the local `market_maker.db`; `test_real_order.py` places actual orders. Do not run them as part of a test suite.

## Server deployment

The app can also run on a Linux VPS behind a domain + HTTPS (`deploy/README.md`, design in
`docs/superpowers/specs/2026-07-27-vps-deployment-design.md`). A single env var,
`PMM_SERVER=1`, switches on all server-only behavior: no `webbrowser.open`, fixed port (no
`pick_port` fallback — the reverse proxy hardcodes it), waitress instead of the Flask dev
server. **It must stay
single-process** — `web/routes.py` holds `db`/`manager`/`encryption_key` as module globals and
the engine runs as in-process threads, so a multi-worker WSGI server would run two engines
over the same wallets. Flask still binds `127.0.0.1` only; Caddy terminates TLS and proxies to
it. `ProxyFix(x_for=1)` recovers the real client IP for login rate limiting (5 failures per IP
→ 15 min lock) — without it every request looks like `127.0.0.1` and the limiter degrades into
a global lock anyone can trip. **The app never self-updates** (no runtime updater, no release
download, no git reset): upstream changes are applied manually via `git fetch -> audit ->
merge -> tests -> deploy` (see `deploy/README.md`).

## Architecture

**Auth gates everything.** Wallet private keys are AES-256-GCM encrypted with a key derived (PBKDF2, 600k iterations) from the user's password (`utils/crypto.py`). The key exists only in memory after login, so engines **cannot auto-start on boot** — the user must log in first. Note `app.py` imports but never calls `init_manager`; the `EngineManager` is constructed inside the `/setup` and `/login` routes (`web/routes.py`) once the encryption key is available. `web/routes.py` holds module-global `db`, `manager`, `encryption_key` — this is a deliberately single-process, single-user design.

**Threading model (`engine/manager.py`).** One shared `MarketScanner` thread produces an eligible-markets list using a single wallet's API (scanning needs no wallet-specific auth). Each enabled wallet gets a `WalletWorker` with its own thread that (a) places orders from the shared list and (b) monitors fills/stop-loss. The SQLite connection is opened once with `check_same_thread=False` and shared across all threads (`models/database.py`).

**Two operating modes** exposed via `/api/engine/*`:
- *Auto*: `start_all()` runs recovery + wallet workers + a periodic scanner loop.
- *Manual*: separate `scan` / `place-orders` / `start-monitors` endpoints so the user drives each step. Manual scan results are persisted to the `eligible_markets` table and surfaced live via `/api/eligible` (memory while scanning, DB when idle).

**Pipeline: scan → strategy → place → monitor.**
- `engine/scanner.py` filters reward markets (reward ≥ threshold, settlement days, price band, spread, cooldown, an optional market-age floor, and an exact size-tier match: rewards_min_size must equal an enabled size_tiers module) and computes an order price via `engine/strategy.py`. It does **not** filter by balance (the eligible list is shared across wallets with different balances); instead it records a per-market `min_cost = rewards_min_size × ceil_to_tick(reward_range_min)` (the minimum capital to place a reward-qualifying order) that each wallet gates on at placement time. Placement parameters (rule1/2/3 coeff thresholds, the three per-rule 高位系数和门槛 — rule1's is the historical key `gap_high_coeff_sum_min`, rule2/3 default to `0` meaning no gate — and amount_value_table) and the order share count live in per-template `size_tiers` modules keyed by the market's `rewards_min_size` (exact match; a market with no matching enabled tier is never placed, and its resting buys are removed by the dropout-cancel pass on the next placement round). Gap-tier thresholds (gap_wide/mid_cents), cliff probe, exposure and exit parameters stay template-global. The optional market-age floor (`skip_new_markets` / `new_market_hours`, template-level,
default off) skips markets created within the last N hours, using the `created_at` the
CLOB rewards endpoint already returns (no extra request). It applies only to the
categories selected in `skip_new_categories` (+ `skip_new_other` for untagged markets),
both template-level and both defaulting to *everything*, so an upgrade changes no
behavior. The category verdict is **any-hit**: a market whose tags include any protected
slug is protected; an untagged market (no curated tag at all) follows `skip_new_other`.
That verdict is the same pure function the trading whitelist uses — `market_in_categories`
in `engine/categories.py`, of which `market_wanted` is now a one-line wrapper — so the two
cannot drift. The age floor is judged twice: once in the shared `discover_candidates`,
where `loosest_new_market_hours(templates, tags)` returns a per-market threshold (a market
is excluded only if *every* template would exclude it, i.e. every template has the switch
on **and** protects that market's categories; then the smallest N wins), and once per
template in `prefilter_for_template`. Both fail open when `created_at` is missing or
unparseable, and a template missing the two category keys is treated as protecting
nothing (fail-open in the same direction). When the discovery stage does exclude a market,
it does not re-enter the pool until a later discovery round (`discovery_interval_sec`, 4 h
by default), so the effective protection window is N to N + one discovery interval; when
some template does not protect it, the market stays in the pool and each template's
`prefilter_for_template` cuts at exactly N on the 30-second placement round. Narrowing the
protected categories therefore lets more new markets back into the pool, which costs one
precise-reward fetch for each that also passes the tier/window gate. Turning the switch on drops now-excluded
markets out of the pool, so the usual dropout pass cancels their resting buys — except in a
market the wallet is still cooling down on, which the dropout pass skips.
- **Two placement strategies run side by side, selected per template by `placement_mode`.** Both are pure, fully unit-tested, and the core IP; change either only with corresponding test updates.
  - `gap_single` (default) → `engine/laddering.py`: gap-tier classification plus risk-coefficient selection, shares from the matched `size_tiers` module.
  - `legacy_wall` → `engine/legacy_wall.py`: the v1.0.15 rule, "find the first wall thick enough, rest one level below it". Three paths by tick size and `max_spread`: fine tick accumulates depth until it exceeds `legacy_cumulative_threshold` (6000); `max_spread == 2` only ever inspects bid1 against `legacy_wall_threshold` (2000); `max_spread >= 3` scans down to `best_bid − max_spread × tick` for the first wall. **The first wall locks the decision**: if its next level is below that floor, outside the reward band, or absent, the market is skipped and no second wall is sought. Shares come from `engine/order_sizing.py` (`min` / `custom` / `balance`), NOT from the tier module.
  - `placement_mode` is matched as an exact string: anything other than `"legacy_wall"` falls back to gap_single, which is why stale DB values (v3.3.0 wrote `"laddering"`) cannot silently switch a wallet onto the legacy strategy.
  - Under `legacy_wall` the `size_tiers` module is **only a market filter** — just `size` and `enabled` are read, to decide which reward-share buckets to trade. Its `shares`, the three per-rule selection thresholds, the three high-side gates and the amount-value table are all ignored.
  - `determine_order_price` takes `int(rewards_max_spread)` (so `4.5` truncates to `4`), deliberately preserved from v1.0.15 and affecting only the `max_spread >= 3` price floor. The **reward band itself** must keep using the untruncated float via `reward_price_range(midpoint, max_spread_cents)` — `max_spread × tick_size` is the bug that made 0.1-cent bands ten times too narrow.
  - Both modes share the same cliff veto (`has_cliff_below` in `engine/laddering.py`, one function, two callers) so the placement decision and the monitor's Step 3 `cliff_cancel` cannot drift. Without it the legacy mode would rest a buy every placement round and have it cancelled 5 seconds later, forever.
- `engine/monitor.py` is API-driven, run as one tick (`WalletWorker._tick`). Step 1 (`check_buy_orders`) detects fills via CLOB `get_trades` (flattens `maker_orders` by funder, deduplicates by `(trade_id, order_id)` against a per-monitor trade-history watermark), records the buy for history, sets cooldown, and cancels the filled buy's remaining quantity — it no longer places the sell. Step 1b (`check_exit`) is **position-driven**: it maintains **exactly one** resting SELL per position; the cost basis is **reconstructed** from our real CLOB `get_trades` fills (`position_cost_with_lots` in `engine/take_profit.py`, via the monitor's per-tick `_cost_lots`). **`_cost_lots` must fetch with `get_trades(TradeParams(market=condition_id))`, NEVER `asset_id=`:** Polymarket's `/trades` server-side `asset_id` filter is broken — it returns an empty list even when fills for that exact `asset_id` exist (the account's other query forms return them), which silently left every position 裸奔 because the cost could never be reconstructed (real incident 2026-05-29). Filtering by `market` (condition_id) works, returns both our maker and taker fills for the market, and `extract_fills` then narrows to the specific `asset_id` client-side. The reconstruction itself replays our buys AND sells for the asset in time order, nets sells against buys FIFO, and the **lots that remain are the current position** — their weighted average is the cost. Critically, the reconstructed remaining size must match the Data API position `size` (tolerance `max(1, 0.01·size)`); if it doesn't (CLOB `get_trades` lagging behind the Data API position, or an externally-built/transferred position), the cost is treated as **unknown → skip**. This replaced an earlier "newest-to-oldest accumulate buys until size is covered" rule that ignored sells: when a recent buy fill hadn't yet propagated to `get_trades`, that rule fell back to an already-sold older buy and priced the sell below true cost, dumping the position at a loss (real incident 2026-05-28). It is **never** the Data API `avgPrice` under any circumstance (it glitches on freshly opened positions, causing undersell; the user banned it outright as a cost source); the Data API position is used only for `size`. **No avgPrice fallback exists:** if the cost can't be reconstructed (no fills, or reconstructed size ≠ position size), the exit *skips* that position (places/touches nothing) and emits a prominent `⚠️跳过·裸奔` warning status row so the unprotected position is visible — we never act on an uncertain cost. The skip self-heals: once `get_trades` catches up, the reconstructed size matches and the sell is placed at/above the true cost on the next tick. The exit is a **two-tier decision** (`check_exit` → pure `plan_exit` in `engine/take_profit.py`; `theta_stop` in price units = ¢/100), and **neither tier ever sells below cost** — the only loss exit is the `B0` backstop: **Tier A** (cost ≤ best_bid, in profit) rests one sell at `max(best_ask, ceil_to_tick(cost))` (maker, capturing the spread rather than dumping at the bid; **floored at cost** — in a clean book `best_ask ≥ best_bid ≥ cost` so the floor is a no-op, but it defends against an abnormal/crossed/phantom-bid snapshot where `best_ask < cost ≤ best_bid` would otherwise rest below cost; falls back to `ceil_to_tick(cost)` when there is no ask); **cost > best_bid** (break-even/underwater) rests one sell at `ceil_to_tick(cost)` (maker `B_park`, waiting for recovery at break-even — **never below cost**, regardless of where the ask sits; this is the fix for the "买15卖13.5 / 买19.3卖18.7" undersell the user reported 2026-06-23, where the earlier "park at best_ask" rule rested below cost whenever the position was underwater by more than the spread). The single backstop: once the loss (cost − best_bid) ≥ `theta_stop` it market-sells (`B0`, FAK stop-loss) to cap extreme drawdown (no bid → no loss computable → no B0, just rest at cost). The user reversed the two branches on 2026-06-23: profit→ask (was profit→cost), underwater→cost (was underwater→ask). The B0 market-sell's **recorded fill price** (the `trades.stop_loss` row, the `exit_market` action, and the status row) is computed by `market_fill_price(resp, best_bid, cur)` (`engine/take_profit.py`), **never the Data API `curPrice`**: curPrice often diverges from the live book (thin reward markets), and recording it made a real 6.5¢ stop-loss display as a *profit* at 0.13 while the FAK actually filled near best_bid ~0.06 (real incident 2026-06-24). `market_fill_price` prefers the market-order response's `takingAmount/makingAmount` avg (only when the ratio is a sane price in `(0,1]`), else falls back to `best_bid` (the FAK's starting fill level, always present when B0 fires), else `cur`. The displayed price is labeled "成交≈买一…（精确成交以链上为准）". Defense-in-depth for the "never sell below cost" invariant: in addition to `plan_exit` flooring both rest branches at `ceil_to_tick(cost)`, `_exit_position` **hard-clamps** the rest price to `≥ ceil_to_tick(cost)` right before `place_limit_sell` (logging a WARNING if it had to clamp — that would mean `plan_exit`/cost produced a sub-cost price, the signature of a bug), and `_exit_position` logs every exit decision at INFO (`离场决策 asset=… 成本=… 买一=… 卖一=… → tier/action/挂价`) so a recurrence of the unexplained "买14卖13" sub-cost fill (user-reported 2026-06-24, root cause not yet isolated: either a wrong-low reconstructed cost, or a profit-branch rest into a phantom bid) can be caught red-handed from the log. `theta_loss` and `case_a_mode` are no longer used (signature kept to avoid churning the call site); the old `B_sweep` capped-loss tier and the case-A market/cost modes were removed. `plan_take_profit` keeps **exactly one** resting sell at the planned price, cancelling/replacing mismatches. This replaced the old per-fill sell, which split one position into many orders priced off divergent per-fill `maker_orders` data. If a sell/stop-loss is rejected by the CLOB (`OrderRejected`), `check_exit` emits a prominent `⚠️…失败·裸奔` status row instead of failing silently, so the now-unprotected position is visible (the order was already cancelled before the failed replace). Both the take-profit and stop-loss `actions.price_basis` reasons spell out the per-lot cost composition (time + price×share + trade_id, via `describe_cost_basis`) so every sell traces back to the exact buy trades it was costed from. `check_exit`/`check_low_balance` prefetch their per-position data before looping (`_exit_prefetch`): a trades wave 6-way through `parallel_map` keyed by `condition_id` (a market's YES and NO positions share one `get_trades`), then **a single batched `get_orderbooks`** keyed by `asset_id` — **trades first, books second, never reversed**, because the book drives the resting price and the B0 stop-loss trigger while the cost only moves when we ourselves fill. Prefetch workers do pure network reads and **must never touch `db`** (one sqlite connection per thread, never reclaimed). `None` in either table means *the fetch failed* and is not the same as an empty result: a failed trades fetch (`None`) makes `_cost_lots` **re-fetch that market itself, once**, exactly as an un-prefetched caller would — only when that retry also fails is the cost unknown and the position skipped with the ⚠️裸奔 warning row. An empty list is the opposite case (the fetch worked, there genuinely are no fills) and must never trigger a re-fetch. Do not "simplify" the `None` branch back into an immediate skip: it was one, and since the prefetch runs over the wallet's proxy that turned every transient hiccup into an unprotected position — 789 of the 810 ⚠️裸奔 skips on 2026-07-29 (97.4%) landed within 3 seconds of a prefetch failure. Step 3 first re-checks the **bid-ask spread** on each resting buy (`engine/eligibility.py` `recheck_resting_buy`, computed from the live orderbook): if `(best_ask − best_bid)` is at/over `max_spread_cents` it cancels the buy (cancel-only, no cooldown, positions untouched); an undeterminable spread (book side missing) is kept. The market's **real-time daily reward** is then re-checked on each surviving buy (`/rewards/markets/{condition_id}`, the same endpoint and `rate_per_day` sum the discovery stage uses, so the number is directly comparable): a reward below the wallet template's `min_reward_usd` cancels the buy cancel-only (`reward_drop_cancel`, no replace) and writes the fresh reward back into the shared candidate pool (memory + the `eligible_markets` row) so the 30-second placing round, which reads a snapshot up to 4 hours old, does not immediately re-place it. `0.0` cancels (the reward really is zero) while `None` skips that order for this tick (could not be determined) — never a falsy check, and never fail-close: a failed or unparsable fetch cancels nothing (hence `get_rewards_for_market` returns `[]` rather than a partial payload when pagination fails mid-way, since an under-summed reward would cancel an order that was earning). A failed cancel writes nothing back and records no action (retried 5s later); the write-back is wrapped so it can never break the cancel path. This gate deliberately sits **ahead of** the empty-book guard, because the reward judgment needs no orderbook at all and a resting buy in a book with no asks is still fillable by someone market-selling into it — leaving it below the guard would keep such a buy resting AND skip the write-back, reopening the exact 4-hour hole this check exists to close. One rewards fetch per market per tick and **one batched orderbook call per round**: Step 3 prefetches rewards 6-way through `api/proxy.py` `parallel_map`, then takes every book in a single `get_orderbooks` (rewards first, books second — the two are serial, and the orderbook is what the cancel decision reads, so it must be the fresher of the two), and building both from sets of `condition_id` / `asset_id` dedups them for free. Prefetch workers do pure network reads and **must never touch `db`**: `models/database.py` opens one sqlite connection per thread and never reclaims any, so a DB read from a pool thread would leak connections every 5 seconds — the round's DB reads (blacklist, template, rewards TTL) happen once on the main thread and are passed in, as are all cancels, action records and status rows. `parallel_map` re-sets the calling thread's `current_proxy` inside each worker because `ThreadPoolExecutor` does not inherit contextvars: `get_orderbook` self-routes through the instance's `_proxied` wrapper, but `get_rewards_for_market` is a `@staticmethod` that relies entirely on the ambient contextvar, so without that the rewards fetch would go out on the real IP. Surviving buys are then judged on **their own resting price** — `determine_order_price` is neither imported nor called in `engine/monitor.py`, Step 3 never recomputes a target price and never re-places anything; if that resting price falls outside the configured 单价区间 `[min_price_cents, max_price_cents]` (endpoints inclusive, mirroring the scanner's price-band filter) the buy is cancelled cancel-only (`price_band_cancel`, no replace), otherwise it is cancelled (never re-placed — the next `place_orders` round re-places it) if it has drifted outside this tick's reward band `reward_price_range(midpoint, rewards_max_spread)` (`step3_cancel_outofband`); a resting price still inside that band is kept untouched. Last comes the **cliff re-check** (`cliff_cancel`, cancel-only): if there is no bid at all in `[reward_range_min − cliff_probe_cents·0.01, reward_range_min)` the buy is cancelled. Placement judges the same thing before placing, but that is not enough — when a market's budget is exhausted (`budget_ok=False`, typically because the wallet's cash is low and the position already fills the exposure) `place_orders` skips the whole market with `continue`, so its resting buys are never re-judged there; Step 3 is the only pass that still reaches them. Both callers share the pure `has_cliff_below` (`engine/laddering.py`) so the two verdicts cannot drift; `0` (or an empty book, meaning undeterminable) cancels nothing. Both price bounds default to no-op (`0`/`100`) when the settings keys are absent.

**Polymarket access (`api/polymarket_api.py`)** wraps `py-clob-client-v2`. Each `PolymarketAPI` is one wallet. Default `signature_type=2` (POLY_GNOSIS_SAFE), which needs a `funder` address — the user's deposit wallet (the Polymarket Gnosis Safe that actually holds funds), **not** the signer EOA. The user only enters a private key: when `funder` is omitted, `PolymarketAPI` derives it from the signer EOA via `derive_deposit_address` (CREATE2 against the Polymarket Safe factory, using the official `py_builder_relayer_client`), and `api_add_wallet` stores that derived address in the `wallets.funder` column. This derivation is verified to reproduce real deposit addresses. Rewards endpoints are static methods (no auth needed); order placement needs L2 creds derived at construction. **Wallet import has exactly one implementation, `_import_wallet` in `web/routes.py`** (probe proxy protocol → detect signature type → encrypt → `db.add_wallet`): `api_add_wallet` (single) and the batch importer both call it, so the two paths can never drift into different account-type or proxy verdicts. Batch import (`POST /api/wallets/import`, config page textarea of `私钥,代理,备注` lines parsed by `web/wallet_import.py` `parse_import_lines`) runs a **background thread** and reports through `GET /api/wallets/import-status` — one wallet costs a proxy handshake plus 4 balance queries (5-15s), so a dozen wallets would blow a synchronous request. One bad row is recorded as a failed row and the rest still import; the progress snapshot never carries private keys.

**Per-wallet HTTP proxy (`api/proxy.py`).** Each wallet can carry its own proxy (`wallets.proxy` column, **plaintext**; entered as `host:port[:user:pass]` in the wallet config UI, `parse_proxy` turns it into `http://user:pass@host:port`); `PolymarketAPI(proxy=...)` then routes **all** of that wallet's network egress through it for IP isolation. The hard part: `py-clob-client-v2` makes every CLOB call through a **process-global** `httpx.Client` (`http_helpers/helpers._http_client`) with no per-instance proxy, and the *same* `PolymarketAPI` is used from two threads (the shared scanner thread places orders; the wallet's monitor thread runs `_tick`) — so the proxy can't be thread-local. The fix is a `contextvars.ContextVar` (`current_proxy`): `install_clob_proxy()` (idempotent, called in `PolymarketAPI.__init__`) swaps the global `_http_client` for a dispatcher that picks/caches a per-proxy `httpx.Client(proxy=...)` by `current_proxy.get()`, and the 9 `requests.get` calls become `http_get` (injects `proxies=` from the same contextvar). Who **sets** the contextvar: every instance network method is wrapped (`_PROXIED_METHODS` loop applies `_proxied`, reading `self.proxy_url`) so CLOB/Data calls self-route regardless of caller (routes, workers); the **static** rewards/gamma helpers carry no wallet identity and instead rely on operation boundaries that set the ambient proxy — `_worker_proxied` on `WalletWorker._tick`/`place_orders`, and a `use_proxy(...)` around the scanner's `fetch_candidates` (so discovery + manual scan use the *scanning* wallet's proxy; orderbook fetches already self-route via the scanner-wallet `PolymarketAPI`). **No fallback to direct:** if a proxy is down the call raises and that wallet's round is skipped — we never leak the real IP. A wallet with no proxy configured (`proxy_url=None`) connects directly (the dispatcher's `None` key reuses the original client), so non-proxied behavior is unchanged. **HTTP and SOCKS5 are both supported** (`socksio` for httpx, `PySocks` for requests — both are lazy imports, hence the explicit `hiddenimports` in the PyInstaller spec — and note that a `hiddenimports` entry for a package **not installed in the build environment** silently collects nothing (PyInstaller only records it in `build/*/warn-*.txt` as "missing module named ..."). The Windows package is built on the maintainer's own machine, not in CI, so `pip install -r requirements.txt` must actually be current there or the installer ships without those lazy imports; every Windows build up to v8.2.0 went out without `socksio`, which silently broke SOCKS5 proxies for the packaged app since all CLOB traffic goes through httpx. Both spec files are covered by `*.spec` in `.gitignore` and are in the repo only because they were `git add -f`'d — check `git ls-files "*.spec"` after touching them, or the change lives on one machine only (`MarketMaker.spec` was untracked until 2026-07-30 for exactly this reason)). The user doesn't know which protocol their provider handed them (iproyal's datacenter IPs, for instance, only speak SOCKS5 even though the credentials look identical), so they still type just `host:port[:账户:密码]` and `probe_proxy` (called by `api_add_wallet` / `api_set_wallet_proxy`, **not** by the engine) settles it at save time: try HTTP, then SOCKS5, whichever reaches `clob.polymarket.com/ok` wins, and the winning protocol is written back into the stored string as a `socks5:` prefix so the runtime never guesses. SOCKS5 always resolves to `socks5h://` (**remote DNS**) — `socks5://` resolves the hostname locally, which leaks DNS from the real IP and in practice got refused by the tested proxies. A proxy that answers neither is **rejected at save time** (400, nothing written): storing an unreachable proxy would silently park that wallet forever, since there is no fallback to direct. The save response carries the detected protocol and the exit IP (best-effort via ipify; a failed lookup doesn't fail the save) so the UI can confirm IP isolation.

**No author/relay reporting.** All PnL, balances and trading statistics stay local (daily
ledger in SQLite, `盈亏台账` UI). There is no weekly push, no Telegram relay, no Cloudflare
Worker and no `REPORT_URL`/`REPORT_KEY` anywhere in the codebase — wallet addresses, PnL
numbers and balances are never transmitted to author-controlled services. `tests/test_no_telemetry.py`
scans the runtime code so any reintroduction fails CI.

## Critical behaviors to preserve

- **Every market sell must pass the book's real `tick_size`.** `place_market_sell` defaults to `"0.01"`, so on a 0.1-cent market an order built from that default is rejected client-side with `invalid price (0.001), min: 0.01 - max: 0.99` — the sell never reaches the CLOB. All three market-sell paths (`_exit_position`'s B0 stop-loss, and `_market_dump`, shared by the resolution dump and the low-balance liquidation) take `tick_str` from `_sell_book` and pass it through. Missing it does not fail loudly: the position just keeps retrying every tick and stays exposed the whole time (2026-07-29 log: 385 rejections, one position unprotected for 10 hours). The limit-sell path always passed it; only the market sells were missing it.
- **Batched orderbooks must be matched back by `asset_id`, never by index.** `PolymarketAPI.get_orderbooks` (CLOB `POST /books`) is what Step 3, `_exit_prefetch` and the scanner's `refresh_orderbooks` all use instead of one `GET /book` per token — measured 18.7× faster (20 tokens: 10.51s serial → 0.56s batched), and Step 3's book wave was the single largest term in tick latency (2026-07-29 production log: median 10.7s / p90 17.3s at 51+ resting buys, while the decisions themselves take milliseconds — 90% of consecutive decision log lines are <10ms apart). The response **silently drops tokens it cannot serve** (HTTP 200 with fewer entries than requested), so zipping the response against the request list shifts every later book one slot up — Step 3 would judge a cancel against another market's book and the exit would price a sell off another asset's best bid, both silently. The wrapper returns `{token_id: book_or_None}` keyed off each entry's own `asset_id`; `None` keeps its existing meaning of *fetch failed* (skip), distinct from a fetched-but-empty book. Single-call ceiling is between 500 (OK) and 1000 (HTTP 400); `_BOOKS_BATCH_SIZE` is 100 and each batch has its own try, because a batch lives or dies as a unit. When the whole call raises, `_exit_prefetch` writes **nothing** (leaving `_MISSING`, so `_sell_book` self-fetches per position) rather than writing `None`, which would close off that fallback — same reasoning as `_cost_lots` retrying a failed trades prefetch.
- **Stopping the engine stops stop-loss monitoring.** `stop_all`/`stop_wallet` cancel open buy orders but also kill the monitor thread, leaving existing positions unprotected — the user-facing messages already warn about this; keep the warnings.
- **Startup recovery** (`startup_recovery` → `init_watermark`) seeds each monitor's trade watermark from DB trade history AND **primes `_seen_fill_keys` with every fill currently on record** (`get_trades(maker_address=funder)`). The watermark (DB `created_at`, local time) is only a conservative lower bound vs the exchange `match_time` that `get_trades(after=)` filters on, so it intentionally re-fetches a recent window; the precise dedup is `(trade_id, order_id)`. That dedup set lives only in memory, so before priming it a restart re-processed already-handled fills — re-recording `cancel_remainder` and re-setting cooldown for markets whose position was long closed (real 2026-05-29 observation). Priming it means **only fills that occur after startup trigger `_handle_fill`**; pre-startup/offline fills are not re-handled by Step 1 (the position they created is still protected by the position-driven take-profit, independent of Step 1). It no longer cancels stale orders or reconciles DB positions.
- **Balance is re-read before every order placement** (not cached per batch) so concurrent fills don't cause overspend — see commit history; preserve this (do not turn it into a per-round cache). It is wrapped in try/except and a failed read skips only that one market: it used to be the sole unguarded network call inside the market loop, so one proxy hiccup aborted the entire round — and since markets are iterated in a fixed `market_competitiveness` order, the ones sorted last were systematically starved of both placement and cancellation (2026-07-29 log: 159 aborted rounds, each preceded by a `get_balance failed` for the same wallet). `place_orders` also reads each wallet's balance up front and skips any market whose recorded `min_cost` exceeds it, before fetching the orderbook.
- **UMA resolution guard cancels buys in resolving markets.** Once someone proposes a resolution on UMA, the Gamma market's `umaResolutionStatus` flips from `None` to non-empty (`proposed`→`disputed`→`resolved`) **while `acceptingOrders` stays `True` and `closed` stays `False`** — so the existing `closed`/`acceptingOrders` signals miss this window and a resting buy could still fill into a market about to settle. `engine/resolution.py` `in_resolution(status)` (non-empty = in resolution) gates two independent points (mirroring the blacklist's multi-point pattern): the monitor's `check_resolution` (runs each `_tick`, right after `check_buy_orders`) cancels **all BUY orders** for any market we hold buys in whose status is non-empty; `place_orders` skips placing into such markets so the cancel doesn't churn against the placement loop (different threads). Status is batch-fetched via `PolymarketAPI.gamma_resolution_status(condition_ids)` (Gamma `/markets?condition_ids=`), which **fails open** (`{}` on any Gamma error → cancel/skip nothing) so a transient outage never mass-cancels. Positions are now **market-sold on resolution** (position-side guard, added after the buy-side one): `check_exit` batch-fetches the `umaResolutionStatus` of the condition_ids it holds positions in and, for any market in resolution, routes that position through `_resolution_dump` — cancel the resting SELL, then `place_market_sell` regardless of P/L, **overriding the "never sell below cost" invariant in resolving markets** (a maker sell parked at cost may never fill before settlement, leaving a losing side to settle to 0). The dump sells **even when cost can't be reconstructed** (normal exit would skip with ⚠️裸奔; here skipping means settling to 0), records the fill via `market_fill_price` (**never** Data API curPrice), and reuses the `stop_loss` trade row (pnl only when cost known — a profitable resolution exit therefore also shows as `stop_loss` in the raw `trades` history, but the `exit_market` action reason spells out it was a resolution dump). If the book has **no bid** (empty or unfetchable — plausible when a losing side's book empties before settlement), it cannot market-sell into nothing: it emits a ⚠️ exposed-position status row and retries next tick rather than recording a phantom fill at the forbidden curPrice. Fail-open: Gamma `{}` → nothing is in resolution → every position takes the normal `check_exit` path. Always-on, no config key.
- **Low-balance liquidation market-sells positions to free cash.** When a wallet's cash `< low_balance_threshold_usd` (template-level, default 4; `0`=off), `monitor.check_low_balance` (runs each `_tick`, **before** `check_exit` — clearing precedes exit) market-sells positions in priority order — tier1: markets with `daily_reward < low_reward_threshold_usd` (default 30, looked up from `eligible_markets` via `db.get_market_daily_reward`), tier2: positions `< small_position_shares` (default 20), tier3: smallest loss first (`engine/liquidation.py plan_liquidation`, pure) — until an **estimated** balance (`+= best_bid×size`, conservative under-estimate so it never over-sells) reaches the target (`liquidate_target_mode`: sell-to-`liquidate_target_usd` or sell-to-`db.get_min_order_cost()`). It **overrides "never sell below cost"** (like the resolution dump). The market-sell machinery is the shared **`_market_dump`** helper (extracted from `_resolution_dump`, which now delegates to it with `expose_on_fail=True`; **the B0 stop-loss branch in `_exit_position` is untouched**). Review-hardened money-path guards: a **60s cooldown after any successful dump** (`LIQUIDATE_COOLDOWN_SEC`) prevents cross-tick over-sell while sold proceeds settle on-chain (the intra-tick estimate only guards one pass; the next 5s tick would re-read the still-lagged low balance and dump more); **`_just_dumped`** (reset each `begin_status_tick`) makes the same-tick `check_exit` **skip** just-sold positions (Data API `/positions` lags, else `check_exit` places a doomed sell for shares we no longer hold and raises a false ⚠️裸奔); **cost-unknown positions are skipped/deferred** (unlike the resolution dump — low-balance has no settlement deadline, so a fresh fill whose cost hasn't reconstructed from `get_trades` is not blind-dumped below unknown cost). **On by default** (threshold 4) — a below-cost-selling behavior change, call it out in release notes.
- **The `orders`/`positions` SQLite tables are no longer the source of truth.** Order management, `/api/positions`, dashboard counts, and the monitor all read the live Polymarket API. The `trades` table only holds `stop_loss` records now — the monitor no longer writes buy/sell rows (per-fill `maker_orders` prices were unreliable). Buy "history" in the UI **is the live Data API position** (`avgPrice`/`size`): the history page's holdings table reads `/api/positions`, and sell/stop-loss actions are shown from the `actions` table ("卖单理由"). The monitor watermark (`init_watermark`) seeds from `max(created_at)` over both `trades` and `actions` so clearing `trades` does not reset it.
- Orders are placed lowest-`market_competitiveness` first (less competition = larger reward share).
- **`wallets.last_active_at` is display-only and must never break trading.** Overwritten (not appended) at two points — a successful `place_limit_buy` in `place_orders`, and a fill detected in `monitor._handle_fill` — each wrapped in try/except that only logs a warning. The dashboard renders it as relative time. A failure to write this column must never abort a placement round or a stop-loss tick.
- Default strategy/risk parameters live in `config.py` `DEFAULTS`; user overrides are stored per-key in the `settings` table and merged on read. Settings changes take effect on next engine start unless restarted.
