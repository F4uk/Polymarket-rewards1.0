# 版本号规范

版本号写在 `version.py` 的 `__version__`,发版时据它打 git tag。格式为三段式 `主版本.次版本.修订号`(即通行的语义化版本 MAJOR.MINOR.PATCH)。

这是一个直接拿真实资金下单的桌面工具,所以判断"算不算不兼容"时,不只看代码接口,主要看三件事:

1. 用户的操作方式变没变;
2. 旧的配置和本地数据能不能原样沿用;
3. 下单 / 做市 / 离场行为和上个版本一不一样。

下面三位的进位规则都以这三点为准。

## 三位分别代表什么

### 主版本(第一位,如 1.x.x → 2.0.0)

有不兼容或颠覆性的改动时进位,并把后两位归零。满足任一条即可:

- 做市、下单或离场逻辑实质改变,用户得重新理解程序会怎么动用资金。例:单边单档策略换成多档梯队(v4)。
- 配置项的含义或结构变了,旧设置没法原样沿用。
- 本地数据 / 数据库格式变更且不向后兼容。
- 操作流程或界面大改,用户要重新学怎么用。例:单页改成 7 屏侧边栏。

一句话:照旧升级就可能被"资金行为变了"打个措手不及的,都算主版本。

### 次版本(第二位,如 2.0.x → 2.1.0)

向后兼容地加东西时进位,把修订号归零:

- 新增功能,比如新页面、新筛选条件、带安全默认值的新配置项。
- 能力增强,但老用户什么都不改也照常能跑。

### 修订号(第三位,如 2.0.0 → 2.0.1)

不改设计意图、只让程序按本该的样子运行时进位:

- 修 bug。例:不足最低份数的档不该挂却挂了、部分成交的残单没按剩余量收敛。
- 文案和界面微调、性能优化、不改行为的内部重构、不影响行为的依赖升级。

## 一次发布同时含多类改动时

按"这次最重的那一类"定位。一次发布既重写了策略(主版本级)、又顺手修了几个 bug(修订级),整体算主版本,后两位归零。小改动不会把大改动"拖低",反过来大改动会盖过小改动。

| 改动 | 进哪一位 | 例子 |
|---|---|---|
| 资金行为变、配置或数据不兼容、界面大改 | 主版本 | v4 多档策略、7 屏前端 |
| 向后兼容的新功能 | 次版本 | 加黑名单页、加筛选项 |
| 修 bug、微调、重构 | 修订号 | 残单收敛、文案修正 |

## 发版步骤

1. 改 `version.py` 的 `__version__`。
2. 写好 `RELEASE_NOTES.md`。
3. 跑 `release.ps1`:构建安装包、算 SHA-256、打 tag、建 GitHub Release。
4. 要撤回某个版本时,发布明确的修复版本；运行中的实例由管理员按部署流程显式更新或回退。

## 附:2.0.0 的由来

v1.0.16 其实一口气并进了 122 个提交:整套 v4 多档做市引擎(SP1-SP6)加全新的 7 屏前端。这是典型的主版本改动,当时却被当成修订号从 v1.0.15 接着往上数。按本规范它本该是 2.0.0。所以撤掉 v1.0.16、把这批改动连同之后的 bug 修复重发为 2.0.0,既对齐了规范,也让版本号第一次名副其实。
