# Polymarket 自动做市系统 — 逻辑与参数说明

> 本文基于真实代码梳理(`engine/`、`api/`、`models/`、`web/`、`config.py`),给出系统的整体架构、各环节逻辑,以及**哪些参数可由用户自定义、哪些是写死在代码里的常量**。
> 适用版本:`version.py` = `1.0.15`。

---

## 1. 这是什么

一个**本地、单用户、单进程**的 Flask 网页应用,自动在 Polymarket 上做"刷流动性奖励"的做市:挂买单 → 监控成交 → 持仓挂止盈卖单 / 触发止损 → 持续维护合规,目标是赚 Polymarket 的流动性奖励而尽量不亏本金。

- 终端用户是非技术小白:双击可执行文件 → 自动开浏览器 → 输入钱包私钥 → 程序自动跑。
- 所有界面文案为**简体中文**。
- 打包为单一可执行文件(Windows 用 PyInstaller + Inno Setup,macOS 出 `.dmg`)。

启动入口 `app.py`:
- 监听 `http://127.0.0.1:8765`(端口被系统占用时 `pick_port` 自动回退到空闲端口)。
- 首次运行没设密码时,浏览器自动打开 `/setup`;否则打开根页面。
- 收到 `SIGINT/SIGTERM` 时优雅关停(停引擎、关数据库)。

## 2. 安全与鉴权(为什么不能开机自启)

- 钱包私钥用 **AES-256-GCM** 加密后存入 `wallets.encrypted_key`(`utils/crypto.py`)。
- 加密密钥由用户密码经 **PBKDF2-HMAC-SHA256、600,000 次迭代**派生(32 字节)。
- 派生出的密钥**只存在内存中**(`web/routes.py` 的模块全局 `encryption_key`);磁盘上只存密码哈希和 salt,从不存密钥本身。
- **后果:引擎无法开机自启动。** 必须先登录(提供密码)才能解密私钥 → 才能构造 `EngineManager`。`app.py` 虽然 `import init_manager` 但从不调用它;`EngineManager` 是在 `/setup`、`/login` 路由里、拿到密钥之后才构造的。
- 这是刻意的单进程、单用户设计:`web/routes.py` 用模块全局 `db` / `manager` / `encryption_key`,SQLite 用一条连接 `check_same_thread=False` 跨线程共享。

| 安全参数 | 值 | 性质 |
|---|---|---|
| KDF | PBKDF2-HMAC-SHA256 | **定死** |
| 迭代次数 | 600,000 | **定死** |
| 加密算法 | AES-256-GCM,12 字节随机 nonce,无 AAD | **定死** |
| 登录密码 | 用户设置(≥6 位) | **用户自定义** |

## 3. 线程模型(`engine/manager.py`)

```
EngineManager
├── 1 个共享 Scanner 线程         —— 用某一个钱包的 API 扫市场(扫描不需要钱包专属鉴权)
│                                    产出"合格市场列表"(eligible_markets),所有钱包共享
└── 每个启用钱包 1 个 WalletWorker 线程
    ├── place_orders()  从共享列表挂买单(下单前按本钱包余额、上限再过滤)
    └── _tick() 监控循环 每 fill_check_interval_sec 跑一遍:
        Step1  check_buy_orders   —— 检测成交
        Step1b check_take_profit  —— 维护止盈卖单
        Step2  check_stop_loss    —— 止损
        Step3  check_sell_orders  —— 在挂买单合规复查
```

- 每个监控 tick 被 `try/except` 包裹:任意一步抛异常只记日志、循环继续——避免一次偶发错误把监控线程**永久杀死**(否则会失去成交检测和止损)。
- **停引擎 = 停止损。** `stop_all` / `stop_wallet` 会撤掉未成交买单,同时杀掉监控线程 → 已有持仓将失去止损保护。界面对此有明确警告,务必保留。

## 4. 核心流水线:扫描 → 策略 → 下单 → 监控

### 4.1 扫描选品(`engine/scanner.py`)

按以下顺序过滤奖励市场(不在此处按余额过滤,因为列表对所有钱包共享):

1. **拉市场**:`/rewards/markets/multi`,按 `rate_per_day` 降序。**不传 min/max_price**——服务端价格过滤 + 按 rate 排序会让该接口卡死/超时/HTTP 500(价格在客户端 Step 5 再筛)。
2. **日奖励门槛**:市场 `rewards_config` 的 `rate_per_day` 之和 ≥ `min_reward_usd`。
3. **结算天数**:剩余天数若落在 `[0, min_settlement_days)` 则排除(已过期 / 负数视为通过)。
4. **黑名单 + 冷却**:`condition_id` 在全局黑名单、或该钱包对该市场处于冷却中 → 跳过。
5. **精确奖励**:`/rewards/markets/{condition_id}` 复核,再次要求 ≥ `min_reward_usd`。
6. **价格区间**:token 价格(乘 100 转美分)落在 `[min_price_cents, max_price_cents]`。
7. **快速价差**:`GET /spread`,价差(美分)≥ `max_spread_cents` 则跳过。
8. **完整盘口**:`GET /book`,用买一确认价格区间,算出奖励区间 `reward_price_range(midpoint, max_spread)`,再调 `determine_order_price` 得出挂单价;算不出价就跳过。

每个合格 token 记一条 `eligible` 记录,其中包含一个关键字段:

> **`min_cost` = `rewards_min_size × ceil_to_tick(reward_range_min)`** —— 在该市场挂一笔"能拿奖励的最小单"所需的最低资金。扫描阶段不判余额,改为记下这个门槛,**每个钱包在下单时按自己的余额各自闸门**。

### 4.2 挂单定价策略(`engine/strategy.py` — 核心 IP,纯函数、全单测覆盖)

核心思想:**找到买盘里足够厚的一档"墙",挂在它再深一档**——既排在厚墙后面被吃单概率低,又仍在奖励区间内吃返利。

`determine_order_price` 按 **tick size** 和 **max_spread** 分三条路径:

| 路径 | 触发条件 | 规则 | 厚度阈值(定死) |
|---|---|---|---|
| 累积档 `_strategy_cumulative` | `tick_size < 0.01`(0.1 美分市场) | 从买一往下**累加**挂单量,累计首次 **> 6000** 时挂在它的下一档 | **6000** |
| 价差=2 粗档 `_strategy_spread2_coarse` | 1 美分 tick 且 `max_spread == 2` | 买一量 **> 2000** → 挂买二;否则不挂 | **2000** |
| 价差≥3 粗档 `_strategy_spread_ge3_coarse` | 1 美分 tick 且 `max_spread >= 3` | 在 `[买一 − max_spread×tick, 买一]` 区间找第一个量 **> 2000** 的档,挂其下一档 | **2000** |

- **所有路径的共同闸门**:最终目标价必须落在奖励区间 `[reward_range_min, reward_range_max]` 内,否则返回 `None`(不挂)。
- 奖励区间宽度 `d = max_spread_cents × 0.01`(`reward_price_range`)。**`max_spread` 是"美分",不是"tick 数"**——曾因写成 `max_spread × tick` 让 0.1 美分市场窄 10 倍而从不下单(已修)。

> 这三条规则里的厚度阈值(2000 / 6000)和"挂下一档"的逻辑是**写死的策略核心**,改这里必须同步改对应单测。

### 4.3 下单(`WalletWorker.place_orders` + `engine/order_sizing.py`)

下单前每个钱包独立做这些过滤/闸门:

1. **排序**:整个合格列表按 `market_competitiveness` **从低到高**(竞争越小,奖励份额越大)。
2. **每钱包挂买单总数硬上限** = `max_buy_orders_per_wallet`。已有买单超上限时,**保留挂得最久的(队列优先级最高、奖励最多),撤掉最新的多余单**。可用槽位 = 上限 − 现有买单数。
3. 逐市场跳过:在黑名单、已持有该仓、处于冷却、该 token 已有在挂买单。
4. **余额闸门**:`get_balance() < min_cost` 直接跳过(在拉盘口/算策略之前)。
5. 重新取盘口、重算挂单价(下单时再算一次,不复用扫描时的价)。
6. **下单份额** `compute_order_size(mode, price, balance, min_size, custom_usd)`:

   | `order_size_mode` | 份额 |
   |---|---|
   | `min`(默认) | 恒为 `rewards_min_size`(最小合格份额) |
   | `custom` | `floor(min(custom_usd, balance) / price)`,不足 `min_size` → 跳过 |
   | `balance` | `floor(balance / price)`(全额),不足 `min_size` → 跳过 |
   | 未知模式 | 按 `min` 兜底 |

7. **下单前实时重读余额**(不按批缓存),防止并发成交导致超支。注意 maker 买单不锁仓,同一笔余额垫付所有在挂买单,所以跨市场循环时**刻意不递减余额**。

### 4.4 监控四步(`engine/monitor.py`,`WalletWorker._tick` 每 `fill_check_interval_sec` 跑一遍)

**Step 1 `check_buy_orders` — 成交检测**
- 用 `get_trades(maker_address=funder, after=watermark)` 拉成交,按 `(trade_id, order_id)` 去重(内存集合 `_seen_fill_keys`)。
- 命中买单成交后:设置该市场冷却(`cooldown_minutes`)、撤掉同一买单的剩余未成交量(防超买)。**不在此处挂卖单**(止盈由 Step 1b 按持仓维护)。

**Step 1b `check_take_profit` — 持仓驱动止盈(每个持仓恒定一笔卖单)**
- 成本 = 我方真实 `get_trades` 成交的加权均价(见 4.5),Data API 持仓只用来取 `size`。
- 卖价 `take_profit_price = max(ceil_to_tick(成本), 买一 + tick)`(**穿价护栏**:绝不低于成本、永远挂成 maker、绝不穿价市价清仓)。
- 用 `plan_take_profit` 对账,使该持仓**恰好一笔**卖单挂在目标价、覆盖整个 size;价/量不符或被拆成多笔的旧卖单一律撤掉重挂。
- **成本算不出(无成交 / 重建 size 与持仓不符)→ 跳过,不挂任何卖单,并标一行醒目状态 `⚠️跳过·裸奔`**,让未受保护的持仓可见;下个 tick 成交流追上后自愈。

**Step 2 `check_stop_loss` — 止损**
- 成本同样只认 `get_trades` 加权(取不到 → 跳过 + `⚠️跳过·无成本`),现价 `curPrice` 取自 Data API 持仓。
- 触发判定 `stop_loss_triggered`:`curPrice < 成本 × (1 − stop_loss_pct/100)`。
- **二次确认**:`curPrice` 与已被禁用的 `avgPrice` 同源、可能瞬时 glitch,所以只有当真正能卖到的价(买一 `best_bid`)也跌破止损阈值才市价平仓;否则视为数据 glitch,跳过不砸盘(`⚠️跳过·盘口未确认`),下个 tick 自愈。
- 真触发:先撤该持仓所有止盈卖单 → 市价平仓 → 记一条 `stop_loss` 到 `trades` 表。

**Step 3 `check_sell_orders` — 在挂买单合规复查**
1. **黑名单复查**:市场进黑名单 → 撤该买单,绝不重挂。
2. **价差复查** `recheck_resting_buy`:`(卖一 − 买一) × 100 ≥ max_spread_cents` → 撤买单(只撤不重挂,不设冷却,持仓不动);盘口某侧缺失视为未知 → 保留。
3. **每日奖励复查**:实时取 `/rewards/markets/{condition_id}`(同一次响应同时解出 `rewards_max_spread` 与每日奖励),奖励额低于模板 `min_reward_usd` → 撤买单不重挂(`reward_drop_cancel`),并把实时奖励写回候选池(内存 + `eligible_markets` 表),否则 30 秒后的下单轮会拿最长 4 小时前的快照把单挂回来。`0.0` 是奖励真归零(要撤),`None` 是取不到(本轮跳过,不撤不重挂);撤单失败则不写回、不记动作,5 秒后下个 tick 重试。**这道闸门排在下面的「盘口为空跳过」之前**——奖励判定用不到盘口,而薄奖励市场常缺卖单一侧,那些单同样会被别人的市价卖单吃掉。
4. **价格合规**:重算目标价。若目标价超出**单价区间** `[min_price_cents, max_price_cents]`(端点含,与扫描口径一致)→ 撤买单不重挂(`price_band_cancel`);否则按 `needs_replace` 判断——价落在不同 tick 则撤旧重挂,奖励区间内无合规价则撤而不重挂,同 tick 则保持不动。

### 4.5 成本重建(`engine/take_profit.py` `position_cost_with_lots`)

这是整个止盈/止损正确性的地基,踩过两次大坑(详见 [附录 A](#附录-a历史踩坑成本价为什么这么算)):

- 数据源**只用** CLOB `get_trades`,且**必须用 `market=condition_id` 过滤、绝不用 `asset_id=`**(Polymarket `/trades` 的服务端 `asset_id` 过滤失效,会对真有成交的 asset 返回空 → 全仓裸奔);客户端再由 `extract_fills` 按 `asset_id` 收窄。
- 算法:把我方在该 token 的全部成交(买入∪卖出,maker∪taker)按时间正序回放,买入入 FIFO 队列,卖出从最早一笔抵消;**回放完队列里剩下的就是当前真实持仓**,其加权均价即成本。
- **重建出的剩余持仓数量必须与 Data API 持仓 `size` 吻合**(容差 `max(1, 0.01×size)`),否则成本不可信 → 返回 `None` → 走"跳过 + ⚠️告警",下个 tick 自愈。
- **绝不**用 Data API `avgPrice` 当成本(用户明令禁止:它在刚开仓时会 glitch 导致低于成本贱卖);Data API 仅用于取 `size` 和 `curPrice`。

## 5. Polymarket 接入封装(`api/polymarket_api.py`)

- 封装 `py-clob-client-v2`,**一个 `PolymarketAPI` 实例 = 一个钱包**。
- 默认 `signature_type = 2`(POLY_GNOSIS_SAFE,智能合约钱包),需要 `funder` 地址(真正持币的 Polymarket Gnosis Safe 存款钱包,**不是** signer EOA)。
- 用户只输入私钥:`funder` 省略时由 signer EOA 经 `derive_deposit_address`(对 Polymarket Safe 工厂做 CREATE2)推导,`api_add_wallet` 把推导出的地址写入 `wallets.funder`。
- L2 凭证在构造时生成(`create_or_derive_api_key`)。
- 抵押币是 **pUSD**(6 位精度,余额 = 原始值 / 1e6),查资金别查 USDC。`balance-allowance` 不发 funder,服务端按 EOA+sig 推地址——所以"哪个 sig 有钱 = 真实账户类型",导入钱包时逐 sig 探测自动判定。
- 奖励类接口是静态方法(无需鉴权);下单需要构造时派生的 L2 凭证。

| 封装里写死的关键项 | 值 | 性质 |
|---|---|---|
| Host | `https://clob.polymarket.com` | **定死** |
| Chain ID | 137(Polygon) | **定死** |
| Data API | `https://data-api.polymarket.com` | **定死** |
| 限价买/卖单类型 | `GTC`(挂着等成交) | **定死** |
| 市价卖单类型 | `FAK`(fill-and-kill) | **定死** |
| `neg_risk` | 三个下单方法默认 `None`(由 CLOB 按 token 自动判定,**不再写死 False**) | **定死(行为)** |
| 下单成功判定 | 状态 ∈ `{live, matched, delayed}` 才算成功,否则抛 `OrderRejected` | **定死** |
| `get_rewards_markets` | `page_size=100`、`max_pages=5`、`rate_per_day` 降序、每页重试 3 次/sleep 2s、timeout 30 | **定死** |
| 余额精度 | `/1e6`(pUSD 6 位) | **定死** |

> 下单封装的几类历史隐性坑(`neg_risk` 写死 False 致负风险仓裸奔、不查返回 status 致幻影止损、止损用 FOK 大仓止不了损)已于 2026-06-02 资金路径审计逐条 TDD 修复。

## 6. 数据存储(`models/database.py`,SQLite,单连接跨线程共享)

| 表 | 作用 | 备注 |
|---|---|---|
| `settings` | 用户参数覆盖 | **key-value**,值为 JSON;读取时 `DEFAULTS` 打底、用户覆盖优先 |
| `auth` | 密码哈希 + salt | 单行 |
| `wallets` | 钱包 | `encrypted_key`(私钥密文)、`funder`、`signature_type`(默认 2)、`enabled`(默认 1) |
| `trades` | **仅** `stop_loss` 记录 | 不再写买/卖逐笔(每笔 maker 价不可靠) |
| `actions` | 改单动作流水(下买单/撤单/止盈/止损…) | "卖单理由"页读这里,含逐笔成本构成 |
| `cooldowns` | 成交后冷却 | `expires_at` 绝对时间戳;`set_cooldown` 入参单位为**分钟** |
| `eligible_markets` | 扫描结果持久化 | 含 `min_cost`、`reward_range_*`、`tick_size`、`neg_risk` 等 |
| `market_meta` | 市场名 + slug(供显示与链接) | 不随扫描清空,逐次累积覆盖 |
| `blacklist` | 全局黑名单 `condition_id` | `get_blacklist_ids()` 返回 set 供热路径查 |
| `orders` / `positions` | **已不再是事实来源** | 订单/持仓/看板/监控全部读实时 Polymarket API |

> **重要**:`orders` / `positions` 表已废弃为事实来源。订单管理、`/api/positions`、看板计数、监控都读实时 API。买入"历史"实为 Data API 实时持仓(`avgPrice` / `size`)。监控 watermark 从 `trades` 和 `actions` 的 `max(created_at)` 取,所以清空 `trades` 不会重置 watermark。

## 7. 两种运行模式与 Web 接口

### 自动模式 vs 手动模式

| | 自动模式 | 手动模式 |
|---|---|---|
| 入口 | `POST /api/engine/start-all` | 分步:`scan` / `place-orders` / `start-monitors` |
| 行为 | 恢复 + 钱包 workers + 周期扫描循环(每 `scan_interval_sec` 扫一轮并自动派发下单) | 用户自己驱动每一步 |
| 停止 | `stop-all`(撤买单 + 停监控,**持仓失保护**) | `start-monitors` 单独跑监控 |

`startup_recovery` → `init_watermark`:用 DB 历史播种每个监控的成交 watermark,并**用当前所有在录成交预热 `_seen_fill_keys`**,使重启后只有"启动之后"的成交才触发 Step 1(避免重启重放已处理的旧成交、重复设冷却)。

### 主要路由分组(`web/routes.py`)

- **鉴权**:`/setup`(首次设密码,≥6 位)、`/login`、`/logout`。
- **页面**(均需登录):`/`(看板)、`/config`(参数)、`/orders`、`/history`、`/logs`、`/blacklist`。
- **引擎-自动**:`/api/engine/start-all`、`/stop-all`、`/restart`。
- **引擎-手动**:`/api/engine/start-monitors`、`/scan`、`/place-orders`、`/cancel-all`、`/test-place-orders`(对前几个合格市场试挂最多 **3** 单)、`/<address>/start`、`/<address>/stop`。
- **设置**:`GET/POST /api/settings`(详见下节)。
- **钱包**:`GET /api/wallets`、`/preview`(纯地址推导)、`POST /api/wallets`(增,自动探测 sig 类型)、`DELETE /<address>`、`/<address>/toggle`。

## 附录 A:历史踩坑(成本价为什么这么算)

1. **按单笔 maker 价定卖价** → 多笔成交把一个持仓拆成多笔卖单、且价偏离真实均价。改为持仓驱动单笔卖单。
2. **用 Data API `avgPrice` 当成本** → 刚开仓时 `avgPrice` glitch(0.28 读成 ~0.21),按错价市价贱卖。`avgPrice` 被**彻底禁用**为成本源。
3. **"从新到旧凑 size、忽略卖出"重建成本** → 近期买入成交还没传到 `get_trades` 时,回退到早已卖掉的旧买入,把卖价压到真实成本以下(2026-05-28 事故)。改为 FIFO 回放买入∪卖出、剩余 lots 即持仓。
4. **`get_trades(asset_id=)` 服务端过滤失效** → 对真有成交的 asset 返回空,成本算不出 → **全仓裸奔**(2026-05-29 事故)。改用 `market=condition_id` 过滤 + 客户端按 asset 收窄。

核心原则:**成本不确定就绝不动手**——跳过该持仓(不挂/不碰任何单)并标 ⚠️ 告警,等成交流追上后下个 tick 自愈。
